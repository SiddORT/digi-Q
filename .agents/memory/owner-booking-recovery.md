---
name: Owner booking recovery boundary
description: Explicit same-account recovery and draft-preservation rules, separate from hosted acceptance.
---

Recovery of a missing consulting-owner profile must be explicit, on the existing
account and selected approved location only. An empty directory is neither
consent nor proof that creating a replacement is safe. Reuse a valid same-account
profile; conflicting candidates and inactive profiles need review.

**Why:** The user approved only the existing owner's dombivali recovery, not a
backfill, repeated onboarding, role switch, new account or broader clinical scope.
Earlier local passes and code rollout did not execute the hosted data repair.

**How to apply:** Keep local verification, server rollout and authenticated hosted
recovery evidence separate. Do not substitute fictional fixture success for the
hosted account. Preserve the existing consent and administrative assignments.

Adding clinical capability to an owning Clinic Admin must not remount their
administrative draft or change its branch-query identity when their
administrative scope has not changed.

**Why:** Identity refresh after recovery can otherwise discard the very booking
draft from which the owner started recovery.

**How to apply:** Still clear private data at actor/role boundaries and retain
doctor-role scope restrictions; a new owner doctor identity is not an
administrative-location change.

A failed browser test is not a rollback of recovery already performed by that
test. Reset the disposable recovery fixture before repeating its initial
missing-profile journey, and always restore ordinary Preview afterward.

**Why:** A selector failure can happen after the repair and eligible schedule
have committed, so reusing the same fixture confuses test setup with a product
regression.

**How to apply:** Keep repair persistence and runner verdict separate. Reset only
the opted-in fictional database, never a real owner's profile.
