# DigiQ Doctors — Standard Clinic Page Redesign, Functional Integration & Complete QA

## 1. Objective and Mandatory Instructions

Redesign and implement the existing DigiQ Doctors Clinic Details page to match the supplied, approved Clinic reference and the approved Notifications page styling.

This is a complete implementation task, not a static UI exercise.

The final result must be:
- Visually consistent with the approved DigiQ design system.
- Compact, intuitive, and easy to use.
- The single standard Clinic page across all authorized login roles.
- Fully integrated with existing frontend routes, backend APIs, database relationships, and permissions.
- Free of broken links, dead buttons, duplicate sections, incorrect clinic data, and unresolved defects within the implemented scope.
- Verified through actual application execution and appropriate automated tests.

**Do not begin implementation until the existing codebase and both reference images have been inspected. If an implementation-critical requirement remains ambiguous or conflicting, ask specific questions before proceeding. Do not guess.**

## 2. Strict UI Reference Lock — No Design Assumptions

The supplied reference images are mandatory specifications, not inspiration.

### Reference precedence

- **Notifications screenshot:** authoritative reference for shared visual styling.
- **Clinic screenshot:** authoritative reference for Clinic page layout, information architecture, actions, and UX.
- **Existing codebase:** authoritative source for business logic, routes, data structures, API contracts, permissions, and working functionality.

If these sources conflict, do not silently choose one. Identify the exact conflict and request clarification when it affects implementation.

### Match the approved styling

Inspect and reproduce the reference's:

- Sidebar width and navigation spacing.
- Header height, breadcrumb positioning, and content offsets.
- Page margins, component gaps, padding, and whitespace.
- Font family, typography hierarchy, font sizes, weights, and line heights.
- Button dimensions, padding, borders, and corner radii.
- Input and dropdown sizes.
- Tab height, spacing, active underline, and selected states.
- Card dimensions, borders, and internal alignment.
- Information-row heights and separators.
- Icon size, stroke, and alignment.
- Background, surface, border, and status colors.
- Status badges, notification badges, empty states, and action hierarchy.
- Overall information density and visible content at the approved desktop viewport.

Use the existing design tokens, shared components, and styles from the approved Notifications page wherever applicable.

Measure reference screenshots at their native resolution and inspect existing CSS values rather than approximating values unnecessarily.

**Do not independently increase padding, typography, card sizes, row heights, or whitespace. Do not introduce a new design system.**

If a required dimension or behavior cannot be established from the screenshots or code, ask before making a material design decision.

## 3. Compact UX Requirements

The Clinic page must remain compact and information-dense without sacrificing readability.

- Keep the clinic overview horizontal and compact.
- Use the approved two-column arrangement for Basic Information and Contact Information.
- Keep section headers, rows, buttons, tabs, and controls aligned.
- Avoid oversized cards, unnecessary vertical stacking, redundant headings, and excessive whitespace.
- Do not add decorative summaries or duplicate information.
- Ensure long addresses, emails, and other values wrap naturally without clipping.
- Preserve responsive behavior without compromising the approved desktop layout.

At approximately 1536 × 1024, compare the implementation against the approved screenshot and correct material differences in alignment, dimensions, and spacing.

Do not consider a generic modern dashboard equivalent to the approved design.

## 4. One Standard Clinic Page Across All Authorized Roles

The approved Clinic page must be the **single standard Clinic Details experience throughout DigiQ**, regardless of which login role accesses an authorized clinic.

Inspect the existing roles and access rules before implementing this requirement.

### Shared page requirements

All authorized roles must use the same:

- Clinic page component and layout.
- Typography, spacing, colors, and component styling.
- Clinic overview structure.
- Details, Locations, Staff, Policies, and Activity History tabs.
- Information hierarchy and section placement.
- Responsive behavior and interaction patterns.

Do not create separate role-specific Clinic page designs.

Where existing implementations duplicate the same Clinic UI, consolidate them into shared components when feasible without breaking established routes or functionality.

### Role-based differences

The layout is standardized; access is not.

- Display only clinics and records authorized for the current user.
- Respect existing Super Admin, Admin, Clinic Admin, staff, and other applicable role permissions.
- Preserve existing ownership, clinic assignments, organizational hierarchy, and tenant boundaries.
- Show, hide, or disable actions according to existing DigiQ conventions.
- Enforce all permissions on the backend.
- Prevent unauthorized access through direct URLs, manipulated identifiers, API requests, and alternate navigation paths.
- Never invent a new permission hierarchy.

For the same clinic, different authorized roles must receive the same standard page design while seeing the data and actions permitted by their existing permissions.

## 6. Standard Clinic Page Layout

### A. Application shell

Reuse the existing global application shell, including:

- DigiQ branding.
- Sidebar navigation and workspace indicator.
- Breadcrumb.
- Workspace search.
- Secure workspace indicator.
- Notifications.
- Logged-in user and role menu.
- Sign Out action.

Preserve existing navigation order, labels, permissions, and active-state behavior.

Do not create a second header or sidebar.

### B. Page heading and clinic selection

Include the approved:

- `Clinic` page title.
- Clinic Group selector.
- `Back to Clinics` action.

Requirements:

- Resolve the current clinic using the actual route identifier.
- Populate the selector from authorized clinic records.
- Changing the selected clinic must navigate to the correct clinic route.
- Refresh all clinic-specific data after switching clinics.
- Do not display the new clinic name with stale information from the previous clinic.
- Handle deleted, invalid, or unauthorized clinic IDs correctly.
- Preserve relevant navigation context when returning to the Clinic list, where supported.

### C. Clinic overview

Create the approved compact horizontal overview containing:

- Clinic icon.
- Clinic name.
- Active/inactive status.
- Clinic address.
- `Edit Clinic` primary action.
- `Edit Date & Time Format` action.
- `Clinic-wide Management` action.
- Existing overflow actions, if applicable.
- Linked-locations summary.
- `Check Doctor Booking Readiness` link.

Use actual persisted data and existing workflows.

Do not show fake values, duplicate information, or unimplemented overflow actions.

### D. Clinic navigation tabs

The standard tabs are:

1. Details
2. Locations
3. Staff
4. Policies
5. Activity History

These tabs must be the exclusive navigation mechanism for their respective sections within the Clinic Details page.

**Do not duplicate Locations, Staff, or Policies as additional management cards below the Details tab.**

Use the application's established routing conventions to make tab states URL-addressable.

Requirements:

- Clicking a tab displays the correct content and updates the URL.
- Directly opening a tab URL displays the correct section.
- Refresh preserves the current valid tab.
- Browser Back and Forward work correctly.
- Invalid tab values are handled consistently.
- Clinic identity remains correct when switching tabs.
- Unsaved form changes are handled safely.
- Tab access respects the existing authorization model.

### E. Details tab

Display two compact, balanced columns.

**Basic Information**

Show existing supported fields:

- Clinic Name
- Address
- Web Address
- Status
- Date & Time Display

Include the existing Edit action.

**Contact Information**

Show existing supported fields:

- Primary Contact
- Phone
- Alternate Contact, if supported
- Email for Notifications

Include the existing Edit action.

Requirements:

- Use real API responses and existing data models.
- Render optional or null fields appropriately.
- Preserve text readability and wrapping.
- Include copy controls for suitable fields.
- Provide accessible labels and feedback for copy operations.
- Use existing validation and business rules.
- Persist changes through the actual backend.
- Refresh displayed data after successful saves.
- Preserve entered values and display actionable errors on failure.
- Handle cancellation without accidentally changing saved data.

Do not create separate data models merely for presentation.

### F. Linked Owner Hours

Display the approved compact section below the two information columns.

Include:

- Linked location count.
- Existing `Manage` action.
- Empty-state explanation when no locations are linked.
- `Check Doctor Booking Readiness` link.

When no location is linked, explain that locations must be linked before location-based timings and availability can be managed.

Requirements:

- Calculate counts from actual authorized records.
- Link Manage to the real existing management workflow.
- Distinguish a genuine empty state from a failed API request.
- Refresh the section when relevant relationships change.
- Use the existing booking-readiness logic and dependencies.
- Never report readiness based on fabricated or incomplete data.

## 8. Routes, Links, and Cross-Page Integrity

The Clinic page must integrate with the existing DigiQ application.

### Route requirements

- Reuse actual route definitions.
- Verify every internal link against the routing configuration.
- Support direct URL access and browser refresh.
- Preserve required clinic identifiers and route parameters.
- Prevent invalid IDs from rendering stale clinic data.
- Handle missing resources and unauthorized access appropriately.
- Prevent conflicting or duplicate routes.
- Verify redirects and fallback routes.
- Preserve correct browser Back and Forward behavior.

Do not use `href="#"`, dummy URLs, or arbitrary fallback navigation.

### Cross-page consistency

Verify that changes propagate to relevant existing pages.

Examples:

- Editing clinic information updates the Clinic list and Clinic Details page.
- Linking or unlinking a location updates relevant counts and location views.
- Clinic status changes are reflected in authorized views.
- Staff assignments remain consistent with Users and Staff views.
- Policy changes are reflected wherever the policies are consumed.
- Date/time preferences display consistently across relevant clinic workflows.
- Booking readiness reflects current persisted clinic configuration and related dependencies.

Use the existing data-refresh, cache-invalidation, and state-management mechanisms where available.

Prevent duplicate submissions and duplicate record creation when users retry or revisit workflows.

## 9. Database and API Integrity

Inspect and preserve the existing database schema and API contracts.

Verify relevant relationships, including:

- Clinic primary keys and identifiers.
- Clinic groups and parent-child relationships, where applicable.
- Clinic-to-location associations.
- Clinic-to-staff and user assignments.
- Clinic-to-policy associations.
- Clinic-to-owner-hours relationships.
- Relevant doctor, appointment, and schedule dependencies.
- Tenant isolation and role-based authorization.

Requirements:

- Never associate a record with the wrong clinic.
- Never use display names in place of authoritative identifiers.
- Validate identifiers and authorization on the backend.
- Prevent unauthorized cross-clinic access.
- Prevent orphaned relationships.
- Respect existing foreign-key constraints and deletion rules.
- Use transactions for multi-step operations where needed.
- Handle stale updates and concurrent changes safely.
- Preserve existing audit logging.
- Derive counts from authoritative records.
- Avoid destructive migrations and production-data modifications.

Use isolated test records for destructive testing.

## 10. Error Handling and Application States

Every data-driven section must handle:

| State | Expected behavior |
|---|---|
| Loading | Compact skeleton or indicator consistent with DigiQ styling. |
| Empty | Clear explanation and authorized next action, where applicable. |
| API failure | Actionable error and retry where appropriate. |
| Unauthorized | Correct access-denied behavior without data leakage. |
| Not found | Appropriate handling for missing or deleted clinics. |
| Save success | Confirmation only after backend success. |
| Save failure | Preserve input and display an actionable error. |
| Partial failure | Identify the failed section rather than presenting false empty data. |
| Session expiration | Follow the existing authentication and redirect behavior. |

Do not treat failed requests as empty collections or zero counts.

Do not display stale data from a previously selected clinic while a new clinic is loading.

Prevent duplicate submissions during ongoing operations.

- 1536 × 1024
- 1366 × 768
- 768 × 1024
- 390 × 844

Ensure:

- No unintended horizontal scrolling.
- No overlapping controls.
- No clipped text or broken wrapping.
- No inaccessible actions.
- Appropriate stacking of information columns.
- Usable tables on smaller screens.
- Keyboard navigation and visible focus indicators.
- Accessible names for buttons, tabs, menus, and dialogs.
- Appropriate contrast.
- Text labels for statuses rather than color alone.
- Correct dialog focus management and Escape behavior where applicable.

Use the existing responsive patterns. Do not invent a conflicting responsive design.

## 12. Security and Authorization

Treat authorization as a backend responsibility.

Test applicable existing roles, including Super Admin, Admin, Clinic Admin, and other authorized roles discovered in the codebase.

Verify:

- The same clinic uses the same standard UI across authorized roles.
- Each role sees only authorized clinics and records.
- Editing and management controls reflect actual permissions.
- Direct requests cannot bypass access restrictions.
- Manipulating clinic IDs cannot expose another clinic.
- Hidden controls do not imply backend security.
- Session expiration and logout work correctly.
- Errors do not reveal confidential information.
- Existing CSRF, input validation, and other security protections remain intact.

Do not broaden access or change role permissions to make the page easier to implement.

## 13. End-to-End Testing and Defect Verification

Use the existing test framework and browser automation tools where available. Reuse existing Playwright tests if present rather than adding unnecessary dependencies.

### Build and runtime checks

- Run the documented build command.
- Run available type checks and lint checks.
- Start the application using the established development command.
- Inspect browser console errors.
- Inspect failed network requests.
- Inspect server and database errors.
- Verify the relevant application routes.

### Navigation tests

Test:

- Clinic list → Clinic Details.
- Details → Locations.
- Details → Staff.
- Details → Policies.
- Details → Activity History.
- Direct access to each valid tab URL.
- Refresh and browser Back/Forward.
- Switching between authorized clinics.
- Invalid and unauthorized clinic IDs.
- Global sidebar navigation.
- Logout and session expiration.

### CRUD and relationship tests

In an isolated test environment:

- Read clinic data.
- Edit clinic information.
- Validate invalid inputs.
- Save valid updates.
- Confirm persistence after refresh.
- Cancel changes and verify saved data remains unchanged.
- Link and unlink locations where permitted.
- Update staff assignments where supported.
- Create or update policies where supported.
- Verify relevant activity records.
- Verify counts and cross-page consistency.
- Verify permission restrictions.
- Test failed requests and retry behavior.
- Check that repeated submissions do not create duplicates.

### UI defect tests

Check for:

- Broken internal links.
- Unexpected redirects.
- Dead buttons and unimplemented actions.
- Broken assets.
- Incorrect active tabs.
- Stale data.
- Incorrect counts.
- Duplicate records.
- Text clipping and overlap.
- Horizontal overflow.
- Console exceptions.
- Failed required API requests.
- False success messages.
- Lost form input.
- Unauthorized data exposure.

An HTTP 200 response alone does not prove that a page works. Verify the rendered page, expected content, and successful data operations.

### Cross-role regression

For each applicable existing role:

1. Open the same authorized clinic.
2. Verify identical layout and styling.
3. Verify the correct authorized data.
4. Verify permitted and prohibited actions.
5. Test direct route access and backend authorization.
6. Confirm consistent data after changes are saved by another authorized user and refreshed.

Record actual test results. Do not label untested functionality as passing.
