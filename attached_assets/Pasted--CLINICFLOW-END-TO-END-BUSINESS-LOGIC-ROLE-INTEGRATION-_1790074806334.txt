# 3. ROLE MODEL

ClinicFlow has these roles:

## Super Admin

Platform-wide administration.

Can manage:
- Clinics
- Branches
- Doctors
- Patients
- Users
- Booking QR codes
- Master data
- Reports
- Audit
- Platform settings

Super Admin has platform-wide scope.

---

## Clinic Admin

Clinic-level administration.

Can manage information within assigned clinic scope.

Clinic Admin must NOT receive platform-level privileges such as:
- User administration outside permitted scope
- Master data administration
- Platform settings
- Audit administration

Do not accidentally elevate Clinic Admin to Super Admin.

---

## Doctor

Doctor can manage:
- Own profile
- Assigned clinics/branches
- Own availability
- Date exceptions
- Own appointments
- Relevant patients
- Own queue
- Booking QR functionality available to the existing doctor scope

Doctor must never access another doctor's private operational data.

---

## Receptionist

Receptionist manages:
- Patients within assigned location scope
- Appointments
- Walk-ins
- Staff booking
- Check-in
- Queue operations

Receptionist must only operate within authorised clinic/branch scope.

---

## Patient

Patient can:
- Manage own profile
- Book appointments
- View own appointments
- Cancel where the existing business rules allow
- View own live queue information
- View aggregate queue progress

Patient must NEVER see:
- Other patients' names
- Other patients' mobile numbers
- Other patients' personal information
- Other patients' private appointment information

# 7. APPOINTMENT BOOKING — ONE CONSISTENT ENGINE

All booking methods must use the same underlying appointment creation/business validation.

Booking sources may include:

- Online
- QR
- Walk-in
- Phone

Do not create separate appointment creation logic for each.

The appointment service must validate:

1. Patient exists and is valid
2. Patient is active where applicable
3. Doctor exists and is active
4. Clinic exists and is active
5. Branch exists and is active
6. Doctor is assigned to that branch
7. Doctor is available on the selected date
8. Date is not closed by exception
9. Session is valid
10. Session is not in the past
11. Capacity is available
12. Booking is within the configured booking horizon
13. Actor has permission to make the booking
14. QR context is valid when booking originated from QR
15. Duplicate booking/session rules are respected

Do not weaken existing backend validation.

# 12. WALK-IN

Walk-in is different from advance appointment booking.

Expected simple flow:

Receptionist
→ Search/Create patient
→ Select doctor
→ Validate that doctor is available for today
→ Validate queue/session is open
→ Validate capacity
→ Add patient
→ Assign token
→ Patient enters queue

- Past dates
- Closed sessions
- Inactive doctor
- Inactive clinic
- Inactive branch
- Unassigned doctor/branch
- Full queue

Use the SAME queue and token logic as other appointments.

Do not create a separate walk-in queue.
