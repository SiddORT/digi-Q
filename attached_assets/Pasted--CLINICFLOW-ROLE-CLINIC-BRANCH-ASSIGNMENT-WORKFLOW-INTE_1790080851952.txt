# 2. CORE BUSINESS PRINCIPLE

ClinicFlow is a multi-clinic, multi-branch doctor appointment and queue management platform.

The most important relationship in the platform is:

USER
↓
CLINIC
↓
BRANCH
↓
DOCTOR / RECEPTIONIST / APPOINTMENTS / QUEUE / AVAILABILITY

Everything must respect these relationships.

There must never be accidental cross-clinic or cross-branch data visibility.

# 3. ROLE STRUCTURE

The system has the following roles:

1. Super Admin
2. Clinic Admin
3. Doctor
4. Receptionist
5. Patient

Do NOT add unnecessary roles.

Do NOT create role-switching functionality.

The authenticated user's stored role determines the available capabilities.

Server-side authorization is mandatory.

Hiding a button is NOT security.

Every API must enforce authorization independently.

---

# 4. IMPORTANT NEW ASSIGNMENT MODEL

ClinicFlow must support many-to-many relationships between users and clinics.

A user may belong to:

- One clinic
- Multiple clinics

A clinic may contain:

- Multiple admins
- Multiple doctors
- Multiple receptionists

A doctor may work at:

- Multiple clinics
- Multiple branches

A receptionist may work at:

- Multiple clinics
- Multiple branches

Clinic and branch assignments must be represented consistently.

Do NOT create duplicate assignment records.

Do NOT create separate competing assignment systems.

Use one clear source of truth for user assignment.

---

# 5. CLINIC AND BRANCH RELATIONSHIP

Every branch belongs to exactly ONE clinic.

Example:

Clinic A
├── Branch A1
├── Branch A2
└── Branch A3

Clinic B
├── Branch B1
└── Branch B2

Branch A1 MUST NEVER appear as a branch option when Clinic B is selected.

This rule must be enforced:

### FRONTEND
AND
### BACKEND

Never rely only on frontend filtering.

# 18. WHAT IF MULTIPLE ADMINS ARE ASSOCIATED?

Do not implement a fragile "single admin" assumption if the existing database supports multiple administrators.

Before changing the schema, inspect the current ownership model.

If a Doctor can legitimately be managed by multiple Clinic Admins, then the new clinic created by that Doctor must be shared with the appropriate admins according to their existing authorized relationship.

If the existing system has exactly one creator/owning Admin relationship, preserve that relationship explicitly.

Do not silently invent a different ownership model.

The important requirement is:

THE SYSTEM MUST ALWAYS KNOW WHICH AUTHORIZED ADMIN RELATIONSHIP SHOULD RECEIVE THE NEW CLINIC MAPPING.
