# DIGIQ DOCTORS — COMPLETE DOCTOR SCHEDULE MANAGEMENT REDESIGN & IMPLEMENTATION PROMPT

## 1. OBJECTIVE

Improve the existing Doctor Schedule Management experience in DigiQ Doctors, including the Edit Doctor Schedule popup, its role-based behavior, scheduling rules, validation, backend integration, and UI/UX.

The feature must support three user roles:

1. Doctor — manages their own schedule where permitted.
2. Clinic Admin — manages schedules within their authorized clinic scope.
3. Super Admin — manages schedules within their authorized administrative scope.

The final experience must be compact, intuitive, reliable, and easy for non-technical users to operate.

**This is an improvement to the existing application, not a new standalone implementation.**

Inspect the existing Replit project before changing code. Preserve existing business logic, database relationships, APIs, permissions, and design-system conventions wherever possible.

Do not modify unrelated modules.

## 5. ROLE-BASED BEHAVIOR

Use the application's existing authorization model. The following describes intended access boundaries, not permission to grant new privileges.

### Doctor

- View their own schedule.
- Edit their own schedule only when permitted.
- Do not display administrative clinic selectors unless the existing permissions explicitly allow them.
- If multiple permitted locations exist, show only authorized locations.
- Do not permit editing another doctor's schedule without explicit authorization.

### Clinic Admin

- Manage schedules for doctors within authorized clinic scopes.
- Display the Clinic Group selector only when applicable.
- Display the Clinic selector when multiple authorized clinics are available.
- Display the Location selector when multiple locations are available.
- Automatically select the only authorized value when there is exactly one choice.
- Do not allow access to unauthorized clinics, doctors, or locations.

### Super Admin

- Manage schedules within their authorized administrative scope.
- Select Clinic Group, Clinic, and Location as required.
- Maintain valid relationships between all selections.
- Do not allow incompatible or unauthorized combinations.

### Shared rules

- Use one shared scheduling implementation across roles.
- Configure role-specific visibility and permitted actions through existing authorization mechanisms.
- Enforce all permissions on the backend, not just in the frontend.
- Revalidate permissions when saving changes.
- Do not duplicate the scheduling code for each role.

## 7. CENTRALIZED TIMEZONE CONFIGURATION

Timezone must be configured through the existing clinic onboarding or authorized clinic configuration workflow.

It must not be editable within the Edit Doctor Schedule popup.

### Configuration ownership

- Super Admin manages timezone configuration within their authorized scope.
- Clinic Admin manages timezone configuration within their authorized scope, subject to existing permissions.
- Doctor cannot change the clinic timezone through the schedule editor.

### Popup display

Display a compact read-only indicator, for example:

`Timezone: Asia/Kolkata (IST) 🔒`

Requirements:

- Read the saved timezone from the existing clinic/location configuration.
- Use the selected location's timezone where locations have different settings.
- Update the displayed value when the selected clinic or location changes.
- Do not introduce a duplicate timezone field or competing source of truth.
- Use the existing timezone conversion utilities.
- Provide a tooltip explaining that schedule times use the configured clinic/location timezone.

If the timezone is missing or invalid, show a clear warning and prevent saving when a valid timezone is required by the existing scheduling rules.

Do not silently assume a timezone or change stored timezone data.

### Timezone changes

When an authorized administrator changes the timezone:

- Follow the existing application rules for schedules and appointments.
- Preserve historical records.
- Do not silently shift existing appointment times or reinterpret stored values.
- Identify the migration and compatibility implications before implementing any change that could alter appointment timing.
- Keep frontend and backend timezone interpretations consistent.

### Toggle ON

- Display the selected day's time-slot editor.
- Allow adding, editing, and removing slots.
- Require valid time slots when required by existing business rules.
- Preserve all existing supported schedule settings.

## 12. COPY FROM FUNCTIONALITY

The `Copy from` dropdown must list the other weekdays, excluding the currently selected day.

Example, when Wednesday is selected:

`Copy from: [Monday ▼]`

Use the existing design-system dropdown component.

After a source day is selected, allow the user to choose between two supported copy operations.

### A. Copy Entire Schedule

Copy the source day's:

- Working-day state.
- Time slots.
- Supported day-level schedule settings already defined by the current data model.

Do not copy doctor identity, clinic assignment, location assignment, appointment records, or unrelated data.

### B. Copy Selected Time Slot

- Display the available slots from the source day.
- Allow selection of an individual source slot.
- Copy its start time, end time, and compatible slot-level settings.
- Validate the copied slot against existing destination slots.

### Safeguards

- Copy into the unsaved form state first.
- Do not save automatically.
- Confirm before replacing existing destination slots.
- Explain whether the operation replaces the entire schedule or adds a slot.
- Allow cancellation without altering the destination.
- Validate conflicts after copying.
- Never modify the source day.
- Do not allow copying to bypass permissions or backend validation.

If equivalent copy functionality already exists, reuse it.

## 14. DUPLICATE SCHEDULES AND CONFLICT PREVENTION

This is a critical business requirement.

A doctor must not have conflicting active schedule entries or incompatible simultaneous appointments.

Inspect the current scheduling model and determine the actual uniqueness and conflict rules before implementing validation.

### Required checks

- Duplicate schedule entries.
- Duplicate time slots.
- Overlapping slots for the same doctor and applicable schedule context.
- Conflicting clinic/location assignments.
- Existing schedules outside the currently open popup.
- Existing appointment conflicts.
- Concurrent schedule updates.
- Timezone and day-boundary implications.
- Existing overnight schedule behavior, if supported.

### Important distinction

A doctor may be permitted to work across multiple clinics. Do not assume that identical clock-time intervals across different clinics are automatically invalid in every circumstance.

Follow the existing business rules for simultaneous assignments and incompatible bookings.

### Backend enforcement

- Perform conflict validation on the server.
- Use database constraints or transactions where appropriate.
- Do not rely exclusively on frontend checks.
- Prevent simultaneous requests from creating duplicate schedules.
- Return actionable conflict messages.
- Never silently merge, move, delete, or overwrite conflicting schedules.
