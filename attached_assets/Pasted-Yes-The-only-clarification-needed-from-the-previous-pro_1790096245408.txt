````markdown
# CLINICFLOW — USER INVITATION, PASSWORD SETUP & LOGIN FLOW

## IMPORTANT — AUTHENTICATION CHANGE ONLY

Implement the following authentication and user-invitation flow in the existing ClinicFlow system.

### DO NOT CHANGE ANYTHING ELSE.

This is an authentication/invitation enhancement only.

Do NOT change or redesign:

- Clinic ownership
- Admin/Doctor/Receptionist relationships
- Clinic mappings
- Branch mappings
- Role permissions
- Dashboards
- Doctor availability
- Appointments
- Patient management
- Queue management
- Appointment QR
- QR scanning/check-in
- Notifications
- Reports
- Existing business workflows
- Existing UI unnecessarily
- Existing database relationships unnecessarily

Everything that already works must continue to work exactly as it does today.

Before making changes, inspect the existing authentication, user creation, password, login and email implementation and reuse the existing architecture wherever possible.

---

# 1. TWO DIFFERENT AUTHENTICATION FLOWS

ClinicFlow must have two distinct authentication approaches.

## A. Admin / Doctor / Receptionist

These users will use:

**Email + Password**

They will NOT use OTP for login.

The password is initially created by the user through a secure invitation/set-password link sent by ClinicFlow.

Roles covered:

- Super Admin
- Clinic Admin
- Doctor
- Receptionist

## B. Patient

Patients will continue to use:

**Email + OTP**

The patient authentication flow must NOT be changed.

Patients should:

1. Enter their email.
2. Receive OTP.
3. Enter OTP.
4. Verify OTP.
5. Login to the patient system.

Do NOT introduce password setup for patients.

Do NOT send password invitation emails to patients.

Do NOT require passwords for patients.

Do NOT change the existing patient OTP login flow.

---

# 2. ADMIN / DOCTOR / RECEPTIONIST CREATION

Whenever a new:

- Clinic Admin
- Doctor
- Receptionist

is created, the system already captures their email address.

That email address must be used to send an invitation email.

The newly created user should initially be considered:

**Invitation Pending / Password Not Set**

until they successfully create their password.

---

# 3. INVITATION EMAIL

After successfully creating an Admin, Doctor or Receptionist, send an invitation email to the email address captured during user creation.

The email should clearly explain:

> You have been invited to ClinicFlow as a [Admin / Doctor / Receptionist] for [Clinic Name].

The email should contain a clear button/link:

**Set Your Password**

Example:

---

### Subject:
**You have been invited to ClinicFlow**

Hello [User Name],

You have been invited to ClinicFlow as a **Doctor**.

You have been assigned to:

**Clinic:** [Clinic Name]

Please click the button below to set your password and access ClinicFlow.

**[Set Your Password]**

This link is valid for a limited period.

If you were not expecting this invitation, please contact your administrator.

Regards,  
ClinicFlow Team

---

The exact wording can follow the existing ClinicFlow email design.

If a user is mapped to multiple clinics, the invitation should reflect the applicable clinic assignment(s) appropriately.

---

# 4. SECURE SET PASSWORD LINK

The invitation email must contain a secure password setup link.

The link must use a secure, random, time-limited token.

Do NOT put:

- Password
- Plain-text credentials
- Sensitive information

inside the URL.

The token must:

- Be cryptographically secure.
- Belong to the correct user.
- Have an expiry.
- Be single-use.
- Become invalid after successful password setup.
- Become invalid when replaced by a newer invitation.
- Be validated server-side.

Prefer storing a secure hash of the token rather than the raw token.

---

# 5. SET PASSWORD FLOW

When the Admin, Doctor or Receptionist clicks:

**Set Your Password**

they should be redirected to the ClinicFlow password setup page.

The page should contain:

### Set Your Password

- New Password
- Confirm Password

The system must validate:

1. The token exists.
2. The token is valid.
3. The token has not expired.
4. The token has not already been used.
5. The token belongs to the correct user.
6. The user account is active.
7. The token is being used for password setup.

Only after successful validation should the user be allowed to set the password.

---

# 6. PASSWORD SECURITY

Never store passwords in plain text.

Use the existing secure password hashing mechanism if one already exists.

Do not create a second password-storage mechanism if the application already has one.

Passwords must never:

- Be stored as plain text.
- Be returned by APIs.
- Be logged.
- Be included in emails.
- Be displayed in the UI.

---

# 7. AFTER PASSWORD IS SET

After the user successfully sets the password:

1. Securely save the password.
2. Mark the invitation as completed/used.
3. Invalidate the invitation token.
4. Preserve the user's existing role.
5. Preserve all existing clinic mappings.
6. Preserve all existing branch mappings.
7. Preserve all existing permissions.
8. Redirect the user to the Login page.

Show a simple confirmation:

> Your password has been set successfully. Please log in using your email address and password.

---

# 8. LOGIN AFTER PASSWORD SETUP

The Admin, Doctor and Receptionist should then login using:

**Email Address + Password**

No OTP should be required.

The existing role-based authentication should determine where the user is redirected.

### Clinic Admin

→ Existing Admin dashboard

### Doctor

→ Existing Doctor dashboard

### Receptionist

→ Existing Receptionist dashboard

The user's existing role and authorization must determine access.

Do not create separate login systems for each role.

---

# 9. SUPER ADMIN

Super Admin should continue using the existing Super Admin authentication.

Super Admin must NOT be affected by the patient OTP authentication flow.

Super Admin should continue to use the application's password-based authentication.

Do not unnecessarily change the Super Admin login process.

---

# 10. PATIENT AUTHENTICATION — DO NOT CHANGE

This is extremely important.

The invitation/password mechanism described in this prompt applies ONLY to:

- Super Admin
- Clinic Admin
- Doctor
- Receptionist

It does NOT apply to Patients.

Patients will continue to authenticate using:

```text

        ↓

        ↓

        ↓
OTP verified
        ↓

````

Patients do NOT need:

* Invitation emails
* Password setup
* Password reset
* Set-password links
* Password-based login

Do not change the existing patient authentication flow.

---

# 11. EXPIRED SET-PASSWORD LINK

The invitation/set-password link must expire after a configurable period.

Use the existing application security configuration if available.

If no suitable configuration exists, create a configurable expiry setting rather than scattering a hard-coded value throughout the application.

If the user opens an expired link, show:

> This password setup link has expired.

Provide an appropriate option/message indicating that the user should request a new link.

Do NOT allow an expired link to set a password.

---

# 12. RESEND SET-PASSWORD LINK

Super Admin and authorised Clinic Admin users must have the ability to send a new password setup link to users they are authorised to manage.

This is required when:

* The original email was not received.
* The user lost the email.
* The invitation expired.
* The user did not complete password setup.

Provide an appropriate action such as:

**Send Set Password Link**

or:

**Resend Invitation**

Use whichever terminology best fits the existing UI.

---

# 13. NEW INVITATION MUST INVALIDATE OLD UNUSED INVITATION

If a new set-password link is generated before the previous one is used:

1. Generate a new secure token.
2. Invalidate the previous unused token.
3. Send the new email.
4. Keep the same user account.
5. Keep the same role.
6. Keep the same clinic mappings.
7. Keep the same branch mappings.
8. Keep the same permissions.

Do NOT create another user.

Do NOT create duplicate mappings.

---

# 14. PASSWORD RESET FOR EXISTING USERS

Once an Admin, Doctor or Receptionist has already successfully set a password, they should use the normal password reset flow when they forget their password.

Super Admin and authorised Clinic Admin users should be able to initiate a password reset for users they are authorised to manage.

The administrator should only initiate the reset.

The user must create the new password through the secure reset link.

Never allow an administrator to see or set the user's actual password.

---

# 15. CORRECT ACTION BASED ON ACCOUNT STATE

**Send Set Password Link**

If the email address already exists:

A Clinic Admin can own multiple clinics.

A Doctor or Receptionist can be mapped to multiple clinics where permitted.

A Doctor or Receptionist must only be mapped to clinics that their associated Clinic Admin owns/is mapped to.

The password/invitation flow must have absolutely no effect on these rules.

# 18. DOCTOR-CREATED CLINIC

Preserve the existing rule.
