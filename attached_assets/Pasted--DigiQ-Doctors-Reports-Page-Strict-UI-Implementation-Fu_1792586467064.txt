# DigiQ Doctors — Reports Page: Strict UI Implementation, Full Functionality & End-to-End QA

## 1. Objective

Implement the approved DigiQ Doctors Reports page inside the existing application.

This is a complete implementation task—not a static mockup or a visual-only redesign.

The completed page must:

- Match the approved Reports screenshot as closely as possible.
- Follow the established DigiQ visual design system.
- Maintain consistent spacing, sizing, typography, alignment, and component styling.
- Preserve all existing business logic, APIs, database relationships, authentication, and permissions.
- Make every visible control and supported workflow functional.
- Display real report data, accurate metrics, and meaningful charts.
- Integrate correctly with the rest of the application.
- Have no unresolved critical defects within the implemented and tested scope.

**Do not make assumptions about unspecified functionality, data, routes, permissions, or business rules. Inspect the existing project first and ask targeted questions if an implementation-critical detail remains unclear.**

Use the latest approved Reports screenshot as the primary desktop visual acceptance target.

- Status.
- Clinic.
- Apply.
- Clear All.

- Display the actual applied values.
- Removing a chip must update the relevant filter state.
- `Clear All` must reset the supported filters consistently.
- Do not confuse draft filter selections with applied filters.
- Do not show stale chips after a filter reset or clinic change.

### D. Summary cards

Potential metrics shown in the reference include:

- Total Appointments.
- Completed.
- Cancelled.
- No-shows.

Requirements:

- Use actual authorized report data.
- Respect the active date range, clinic, and applicable filters.
- Calculate percentages correctly.
- Handle zero denominators and unavailable comparison periods safely.
- Do not display fabricated values, trends, or percentages.
- Do not assume that all metrics exist in the current backend.

If a metric cannot be supported, identify the missing capability instead of inventing data.

### E. Appointments Trend chart

## 6. Date-Range Selector — Required Behavior

Implement a compact date-range dropdown or calendar popover consistent with the approved styling.

Support these presets when compatible with the existing reporting requirements:

- Today.
- Yesterday.
- Last 7 days.
- Last 28 days.
- Last 30 days.
- This week.
- Last week.
- This month.
- Last month.
- Custom range.

The selected date range must be visible in the closed selector.

### Custom range

- Provide start and end date selection.
- Validate the date range.
- Prevent invalid start/end combinations.
- Respect the application's configured timezone and existing reporting conventions.
- Display dates in the established DigiQ date format.
- Handle inclusive/exclusive boundaries consistently with the backend.
- Prevent accidental off-by-one-day errors.
- Update applied filter chips correctly.

Do not hardcode the reference date as the permanent current date.

Use the real current date and the application's established timezone.

### Comparison toggle

If comparison is supported, allow comparison with the appropriate previous period.

For example, comparing a seven-day period with the immediately preceding seven-day period.

When enabled:

- Use the correct previous period.
- Display comparison values only when valid data exists.
- Calculate percentage changes correctly.
- Distinguish absolute changes from percentage changes.
- Handle zero baselines and unavailable data safely.
- Label the comparison period clearly.

When comparison is unsupported by the current backend, do not fabricate results; identify the missing requirement.
