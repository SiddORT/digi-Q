# CLINICFLOW — FINAL AUTHENTICATION FLOW CORRECTION

Proceed with the authentication implementation, but DO NOT change the existing ClinicFlow business logic, role/clinic/branch mappings, appointment workflows, queue, QR functionality, dashboards, or any other functionality.

The only purpose of this task is to correctly implement the authentication experience for Staff users versus Patients.

## 1. FINAL AUTHENTICATION RULE

ClinicFlow has two completely different authentication flows.

### STAFF USERS

The following roles are Staff:

- Super Admin
- Clinic Admin
- Doctor
- Receptionist

Staff users MUST authenticate using:

**Email Address + Password**

Staff users MUST NOT use the Patient Email OTP login flow.

### PATIENT USERS

Patients MUST authenticate using:

**Email Address + OTP**

Patients do NOT need to create or maintain a password.

Do not apply the staff password/invitation flow to Patients.

---

# 2. DO NOT REPLACE CLERK

Continue using the existing Clerk authentication implementation.

Do not introduce another authentication provider.

Do not create a second authentication system unless it is absolutely required by the existing Clerk architecture.

First inspect the current Clerk implementation and existing authentication code.

Reuse the existing Clerk configuration and SDK wherever possible.

The objective is to correctly separate the application flows by role without breaking the existing system.

# 3. STAFF INVITATION FLOW

Whenever any of the following users is created:

- Clinic Admin
- Doctor
- Receptionist

the system already captures their email address.

After the user is successfully created and the required role + clinic/branch mapping is successfully persisted:

1. Send an invitation email to the user's email address.
2. The email must clearly state that the user has been invited to ClinicFlow.
3. Clearly mention their role:
   - Admin
   - Doctor
   - Receptionist
4. Mention the clinic/clinic(s) they have been associated with where appropriate.
5. Provide a secure link:
   **Set Your Password**
6. The link should take the user to the ClinicFlow password setup page.
7. The user sets their password.
8. Password setup must be completed successfully before the account can use normal staff login.
9. After successful password setup, redirect the user to the Staff Login page.
10. The user logs in using:
    - Email
    - Newly created password
11. After successful authentication, redirect the user to the correct dashboard based on their role.

Do not automatically log the user into the application after setting the password unless the existing Clerk flow requires it and it is secure.

The expected UX should be simple and predictable:

**Invitation Email → Set Password → Staff Login → Role Dashboard**

---

# 4. STAFF LOGIN

Create/maintain a clear Staff Login experience.

Staff login should request:

- Email
- Password

Do not show Email OTP as the normal staff login option.

After successful authentication:

- Super Admin → Super Admin workspace
- Clinic Admin → Admin workspace
- Doctor → Doctor workspace
- Receptionist → Receptionist workspace

Use the existing role resolution and authorization system.

Do not duplicate or redefine the existing role model.

---

# 5. PATIENT LOGIN

Patients are different.

Patient authentication MUST remain:

**Enter Email → Send OTP → Verify OTP → Login**

Patients should NOT be asked to:

- Create a password
- Set a password
- Reset a password
- Use staff invitation links

Do not apply the staff password onboarding flow to Patients.

The patient should be able to enter their email address, receive the OTP, verify it, and enter the Patient experience.

---

# 6. VERY IMPORTANT — ROLE-BASED AUTHENTICATION SEPARATION

Do not rely only on hiding/showing different buttons or screens.

The application must enforce the role-specific authentication flow server-side as well.

Before initiating the Patient OTP flow:

- Resolve the ClinicFlow user associated with the email.
- If that account belongs to:
  - Super Admin
  - Clinic Admin
  - Doctor
  - Receptionist

then DO NOT initiate the Patient OTP login flow for that account.

Show a clear message such as:

"This account is registered as a staff account. Please use Staff Login with your email and password."

Likewise, staff login must authenticate using the password flow.

Do not allow a Staff account to be accidentally treated as a Patient account simply because the same email address was entered into a patient login screen.

The application must determine the user's ClinicFlow role from the authoritative user record.

Do not trust a role supplied by the browser/client.

---

# 7. IMPORTANT CLERK CONSTRAINT

The current Clerk configuration supports both Email OTP and Password authentication, but Clerk's normal session information does not by itself provide a reliable application-level distinction that should be treated as "this session was created using password" versus "this session was created using email OTP."

Therefore:

DO NOT implement an insecure check such as:

- checking only whether a user has a password
- checking only the frontend login page used
- trusting a client-side flag saying "password login"
- storing an untrusted authentication-method value in local storage
- assuming the authentication method based only on the URL

Instead, enforce the role-specific authentication entry points and server-side authorization.

If the current Clerk setup provides a documented and secure mechanism to distinguish the authentication method, use it.

If it does not, do NOT invent or simulate such a mechanism.

The most important security rule remains:

**Staff roles must only be granted Staff application access through the Staff authentication flow, and Patient OTP must not be offered to Staff accounts.**

# 14. DO NOT CHANGE CLINIC / BRANCH / USER MAPPING

This task MUST NOT change the previously implemented ClinicFlow ownership and mapping rules.

Keep these rules exactly as they currently are:

- One Clinic → Exactly one Clinic Admin
- One Clinic Admin → Many Clinics
- One Clinic → Many Doctors
- One Clinic → Many Receptionists
- One Doctor → Many Clinics
- One Receptionist → Many Clinics
- One Receptionist → Many Branches
- One Branch → Exactly one Clinic

A Doctor or Receptionist can only be mapped to clinics owned/mapped to their Admin.

If an Admin owns multiple clinics, the Admin can map a Doctor or Receptionist to multiple of those clinics.

The Doctor/Receptionist must never be mapped to a clinic outside their Admin's clinic ownership scope.

If Doctor X creates a new Clinic and Admin A is the Clinic Admin/owner associated with Doctor X:

- New Clinic → Doctor X automatically mapped
- New Clinic → Admin A automatically mapped as its single Clinic Admin

Do not change any of these rules.
