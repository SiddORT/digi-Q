# Private uploads and stable file URLs

## Scope and rollout boundary

This is the private-file foundation, not a file migration, clinical database,
automated antivirus service, retention policy or production rollout. Clinical and
business records remain relational PostgreSQL data. Files are attachments only.
No existing bytes or locators are moved or rewritten. No live provider is needed
for the tests below.

The opt-in [S3-compatible adapter](s3-private-storage.md) extends this interface.
`FILES_STORAGE` selects new private uploads separately from public logos; blank
preserves the existing `MEDIA_STORAGE` behavior. Apply migration
`0025_private_file_s3` before deliberately selecting S3 on a persistent
environment. It changes only the provider allowlist, not file metadata/locators
or immutable identity/erasure guards. No persistent database has been migrated
as part of the S3 adapter work.

**Apply the reviewed additive migration before running the changed document
routes on any persistent environment.** Migration `0024_private_file_registry`
was authored and rehearsed only in disposable databases. Neither development nor
production application databases were migrated as part of this work.

## Configuration and ownership

Use the existing private environment loading mechanism and
`config/server.env.example`; all credential/address placeholders are empty.
The storage configuration module centralizes `MEDIA_STORAGE`, `MEDIA_ROOT` and
`MEDIA_URL`. Existing integration-vault resolution and its precedence are
unchanged. Storage never writes environment settings or returns them to a client.

- `MEDIA_STORAGE=object` remains the default for **new** files; existing
  Google/Replit App Storage credentials and client initialization are retained.
- `MEDIA_STORAGE=local` requires persistent disk. For new private files,
  `MEDIA_ROOT` must be an absolute directory ending in `uploads`, such as
  `/var/lib/digiq/uploads`, outside `public`/`static` and, in production, outside
  the workspace checkout. Existing logo and historical document root contracts
  remain valid; stricter validation applies to the new private-file writer.
- `MEDIA_URL` remains the separate public-logo handler prefix. **It is not a
  static mount of MEDIA_ROOT and must never become one.**
- Object writes require a valid `PRIVATE_OBJECT_DIR`. New object locators pin
  their bucket/prefix. Historical object documents still resolve their original
  UUID locator under the existing configured patient-document prefix; retain
  that configuration while those documents exist.
- Changing the default driver does not change any file's recorded provider.
  Historical local files still need their original MEDIA_ROOT. Changing a root
  is not a file migration; do not move or remove it without separate approval.

The service account must own private directories, without group/world write.
Symlink components (including root ancestors) and final symlink files are
rejected. Protect parent directories and the service OS account from untrusted
local writers. The adapter is not a sandbox against a compromised service user.

Local layout (the configured root is already `uploads`):

```
uploads/private/clinics/<clinicId>/doctors/<doctorId>/profile/<fileId>.<ext>
uploads/private/clinics/<clinicId>/doctors/<doctorId>/credentials/<fileId>.<ext>
uploads/private/clinics/<clinicId>/patients/<patientId>/profile/<fileId>.<ext>
uploads/private/clinics/<clinicId>/patients/<patientId>/documents/<fileId>.<ext>
uploads/private/clinics/<clinicId>/patients/<patientId>/medical/<fileId>.<ext>
uploads/private/staging/<randomId>
```

Identifiers are checked against existing authorized entities; the file ID and
extension are generated by the server. Display names, contact details, diagnoses
and client-proposed paths never enter storage keys.

Patients have global identities but each attachment belongs to exactly one
clinic. Existing patient self-read, staff clinic scope and doctor visit/handoff
entitlements remain in effect. Profile visibility alone is not clinical file
access. Patients still cannot upload/delete documents. Doctor-owned private files
are restricted to the doctor in that assigned clinic, their owning Clinic Admin,
or Superadmin; receptionists and other doctors cannot read credentials.
Configurable module and clinic-specific custom-role restrictions are checked
using the server-resolved file clinic.

## Registry and migration impact

The existing `patient_documents` table is the **single** file registry, retaining
its historical name and IDs for compatibility. There is no competing metadata
table or attachment-byte column. The additive migration makes patient_id nullable
only to support mutually exclusive patient/doctor subjects, and adds doctor_id,
purpose, digest, registry version, scan/review state, previous deletion state and
update timestamp. Existing provider, locator, size, detected MIME, clinic,
uploader and creation/deletion timestamps remain canonical.

Historical rows remain registry version 0 with their old status, provider and
key. They do not acquire invented digests or restoration evidence. New version 1
rows have database constraints for supported provider/types, one subject,
purpose, size, digest, lifecycle and scan approval; a partial unique index prevents
duplicate provider/locator pairs. A trigger prevents downgrading the registry
version or changing a new file's subject, clinic, locator or byte evidence.
Audit records identify upload, approval, download, delete and restore actors.
Existing uploader anonymization and immutable erased-asset/staff-identity
triggers remain attached to the registry.

Personal doctor files deliberately block that doctor's permanent account erasure
until a separate personal-file byte-erasure policy is approved. Soft deletion
retains bytes and therefore does not clear this blocker. Clinical patient files
remain shared records and preserve anonymized uploader attribution during staff
erasure. Restore does not recreate uploader identities or bypass erasure fences.

## API and security review

All stable routes require the existing authenticated native session. Mutations
retain the application's origin/CSRF controls. File responses, including errors
under these routes, are `private, no-store`. No response reveals storage keys.

| Operation | Contract |
|---|---|
| `POST /api/files` | Raw binary body, maximum 10 MiB; query clinicId, exactly one patientId/doctorId, purpose and display name |
| `GET /api/files/:fileId` | Authorized metadata for active/quarantined files |
| `GET /api/files/:fileId/content` | Approved active bytes only, attachment disposition, sandbox and nosniff |
| `DELETE /api/files/:fileId` | Authorized uploader or clinic administrator; soft deletion |
| `POST /api/files/:fileId/restore` | Same delete authority plus current scope; exact retained bytes and lifecycle required |
| `POST /api/files/:fileId/approve` | Superadmin attestation of completed offline security review, JSON `{digest, reviewed:true}` |

**Every new private upload is quarantined.** MIME sniffing is not a malware scan.
Supported content is PDF, PNG, JPEG, WebP and UTF-8 text; profile purpose requires
a raster-image signature. Active markup/executable text headers are rejected.
Neither a filename extension nor a declared MIME grants approval. Raster
signatures alone are not treated as full image validation or antivirus evidence.

An authorized operator must inspect/scan bytes using a separately operated,
trusted offline process, compare the exact SHA-256 digest, and explicitly attest
the review through the approval route. The endpoint verifies retained bytes and
the supplied digest and audits the release; it does not claim to run a scanner.
Do not approve unfamiliar files merely to make a download work. There is no
public quarantine-download endpoint or automated scanner integration.

Uploads register staging first, write bytes, then become quarantined. Local
completion uses a synced exclusive staging file and an atomic, no-overwrite hard
link on the same volume; staging names are removed. Object completion uses
create-only writes. Failed/uncertain completions remain hidden with a durable
failed registry entry for controlled reconciliation, not automatic deletion.

Existing `/patients/:id/documents` uploads are compatibility facades into this
same workflow. The existing compact uploader now explicitly reports security
review pending; approved documents appear in its unchanged active-file listing.
This foundation does not add an administration review screen. Existing
`/patient-documents/:id` links keep working for historical/approved active files.
Published sanitized clinic logos retain their separate explicit publication flow;
QR/ticket assets and locators are not changed.

## Delete, restore and retention

Eligible deletes retain bytes. They record the former active/quarantined state
and digest, hide the file from metadata/content/old-link reads, and audit the
action. Restore requires current authorization, retained bytes with identical
size and digest, unchanged locked registry state, and passing erasure fences.
Quarantined files restore to quarantine, never to active. Missing/tampered bytes,
already-restored state and old deletions without retention evidence conflict
explicitly. No automatic purge, retention duration or real file relocation is
introduced.

## Durability, backups and platform cases

- Do not use local mode on ephemeral deployment disks. Attach a persistent
  filesystem supporting same-volume hard links. All replicas must share the
  same durable root, or use the object driver.
- Back up PostgreSQL **and** the upload root/object inventory coherently,
  including hidden/quarantined/deleted/failed records and retained bytes.
  Database-only backups cannot restore file contents. Keep erasure fences when
  restoring backups; restoring bytes never authorizes resurrecting erased data.
- Encrypt disk/backups at rest; restrict the service account and backup access;
  monitor capacity. Indefinite retention needs explicit capacity planning.
- A process crash can leave an unreferenced staging name or failed final object.
  Reconcile against the registry before any separately approved cleanup. Do not
  run a blind age-based directory purge.
- Set reverse-proxy body limits slightly above 10 MiB for private uploads.
  No reverse-proxy alias/directory listing may expose the upload root.
- Linux execution verified private modes, symlink rejection, exclusive file
  creation, hard-link completion, no-overwrite failure and byte restoration.
  Portable key/display-name tests reject Windows device names (`CON`, `NUL`,
  `LPT1`), drive/separator/traversal/control characters and unsafe suffixes.
  **No native Windows/NTFS execution, junction-race test, UNC share, Windows ACL,
  antivirus locking, or power-loss durability test was performed.** Validate
  those on the intended Windows host before selecting local mode there.

## Verification

`pnpm --filter @workspace/api-server test:files` exercises real HTTP routes and
the actual migration chain in disposable PGlite/PostgreSQL, real temporary local
files, and an in-memory object-provider double. Coverage includes authorization,
custom roles, clinic separation, old-link/provider reads, quarantine, failed
writes, malicious inputs, retained-byte restore, erasure fences, metadata upgrade
preservation, doctor-erasure blockers and separate public-logo publication.

`pnpm test:migrations` rehearsed all 24 migrations and repeat no-op behavior on
disposable PostgreSQL **15.13 and 16.9**, with no workspace/production database.
Shared-library, API-server and ClinicFlow type checks passed.

The broader staff suite also reported retired-staff appointment fixture
routing and invitation-text assertion failures. The old standalone local-logo
fixture also lacks the current durable staff-dispatch schema/actor setup.
The current full-schema local-logo compatibility case passes in the private-file
suite. No live-provider or native-Windows verification is claimed.
