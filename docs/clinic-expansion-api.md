# Clinic expansion API contract

Implementation contract for the coordinated ClinicFlow expansion. Existing QR,
booking, schedule and queue APIs remain authoritative; no second booking engine.

## Clinic setup and settings

- `GET /api/public/registration-options` (`useGetRegistrationOptions`) is anonymous, rate-limited and read-only. It returns `{categories:[{id,name}],specialities:[{id,name}],qualifications:[{id,name}]}` containing at most 200 active records per allowlisted type. It exposes no users, assignments or private master categories. New unmapped identities must use it instead of protected `/masters`.

- `POST /api/clinic-registration` is the new authenticated self-registration contract. Body `{fullName,mobile?,password,clinic:{name,address,slug,email?,phone?,categoryId?,specialityIds?,referralCode?},branches:[{name,address,slug,city?,timezone?,email?,phone?,inheritEmail?,inheritPhone?,openingHours?:[{dayOfWeek,startTime,endTime}]}],policies?,ownDoctor?:boolean,specializationId?,qualificationIds?}`. Response is `ClinicSettingsResult` (clinic, branches, policies, doctorId nullable). Only a new unmapped Clerk identity with a verified primary email and server-verified password is eligible. Existing app accounts are not silently elevated. Entire application provisioning is atomic, preserving one owning Clinic Admin. Existing invited-admin onboarding is retained.
- `openingHours` are branch weekly intervals, separate from doctor sessions. Absent or `null` means legacy unrestricted; explicit `[]` means all days closed and rejects new bookings. Public responses retain `null` rather than coercing missing hours to `[]`. Nonempty configured hours must contain each doctor session. No data backfill is needed: existing absent fields remain unrestricted.

- `POST /api/clinic-admin-onboarding` retains the existing admin + first-clinic atomic creation.
- `GET /api/clinics/:id/settings` returns the clinic, enriched branches and `policies`.
- `PATCH /api/clinics/:id/settings` accepts `{ clinic?: {name,address,email,phone,slug,categoryId,specialityIds,referralCode}, branches?: [{id?,name,address,city,timezone,email,phone,inheritEmail,inheritPhone,slug}], policies?: {bookingHorizonDays,cancellationCutoffMinutes} }`. Submitted branches are upserted atomically; omitted branches are retained, never deleted. Super Admin selects a clinic; Clinic Admin must own it. Platform settings remain separate.
- Branch `effectiveEmail` and `effectivePhone` are computed live, independently using inheritance flags. Branch overrides are retained when inheritance is enabled.
- Legacy explicit branch contacts remain overrides until deliberately changed; new setup branches default to inheritance. All static application root paths and role roots (`doctor`, `patient`, `receptionist`, `audit`, `qrs`, `exceptions`, etc.) are reserved.
- Slugs are lowercase 3–63 character letters/digits/hyphens, unique for clinics globally and branches within clinic. Reserved root names are rejected. Once set, slug changes return 409; display-name edits do not rename URLs.
- `POST /api/me/doctor-profile` accepts `{specializationId?,qualificationIds?,about?,branchIds: string[]}` and attaches an own doctor profile to the authenticated Clinic Admin without changing account role or ownership. Selected active branches must belong to that admin.
- `/me` already resolves the doctor profile by authenticated user ID, regardless of account role: the response's `doctorId` and `user.doctorId` are populated for consulting Clinic Admins while `user.role` remains `clinicAdmin`.
- Super Admin `POST /api/clinic-admin-onboarding` also accepts `branches`, `policies`, `ownDoctor`, `specializationId`, `qualificationIds`, and the clinic metadata/slug above. Both paths call the same `createOwnedClinic` transaction service; existing invitations remain post-commit.

## Public pages

- `GET /api/public/slug-availability?slug=...&clinicId=...` returns `{available,slug}`. Omit clinicId to check a root clinic slug; include it to check a branch slug. Bounded/rate-limited anonymous read; final writes revalidate transactionally.
- `GET /api/public/clinics-by-slug/:clinicSlug{/:branchSlug}` returns `{clinic:{id,name,slug,address,email,phone},branches:[{id,name,slug,address,city,timezone,effectiveEmail,effectivePhone,openingHours}],branch:null|branch,qrReference:null|string,doctors:PublicDoctor[]}`. A single active branch is selected automatically. Multiple branches require selection. Inactive contexts return 404. GET is read-only: QR is an existing active branch-wide booking QR, provisioned/reused only when an authorized user first saves the branch slug or during registration. Revoked QR returns null, never resurrected by public reads. No patient data.
- Public routes `/:clinicSlug` and `/:clinicSlug/:branchSlug` consume this resolver. `?book=1` uses the existing guest booking; `?display=1` uses the existing display with returned QR reference. Legacy QR links remain supported.
- Resolver `clinic` additionally includes `doctorCount` (distinct active profiles with an active account and active branch assignment in this clinic) and nullable `averageConsultationMinutes`. Each returned doctor includes nullable `averageConsultationMinutes` and `expectedDurationMinutes`. Actual means are calculated from valid completed consultation start/end timestamps; no completions means null, never zero/configured duration. Doctor expected duration is the explicit clinic configuration or null. Scheduling and queue details use the existing availability-session and public-display APIs with the selected live context.

## Live presence

- `GET /api/doctors/:id/presence?branchId=...&date=YYYY-MM-DD&sessionId=...` returns `{doctorId,branchId,date,sessionId,status,updatedAt}`.
- `PATCH /api/doctors/:id/presence` accepts `{branchId,date,sessionId?,status:"available"|"onBreak"|"away"}`. Doctor can alter own profile only; clinic administration is ownership scoped. Absence of a stored presence means available for legacy compatibility.
- Presence changes are audited and do not alter weekly schedules or future bookings. Automatic calling is suspended while unavailable; finishing a current consultation remains allowed.

## Session isolation

- Existing schedule `id` is the `sessionId`; weekly schedule CRUD now permits non-overlapping sessions on the same doctor/branch/weekday. Existing IDs remain unchanged.
- `GET /api/public/availability` retains its single-session result and accepts optional `sessionId` or `startTime`. `GET /api/public/availability/sessions?doctorId=...&branchId=...&date=...` returns an array of the same availability objects, each including `sessionId`. The single endpoint returns 409 if multiple sessions exist and none is selected.
- `GET /api/session-contexts?doctorId=...&branchId=...&date=...` (`useGetSessionContexts`) is authenticated and scoped to Super Admin, owning/assigned Clinic Admin, own Doctor, or assigned Receptionist. It returns availability-shaped `SessionContext[]` with `snapshotOnly:boolean`, merging current templates and persisted appointment start-time snapshots. Historical-only entries use `available:false`, `remainingTokens:0`, and a descriptive reason; they do not authorize bookings. No patient identity, appointment reference or token is exposed. Staff selectors must key/select by `startTime` as well as `sessionId`, since an edited template ID can have old and new timings. Public booking selectors keep using public availability.
- `GET /api/queue` never inserts settings or updates appointments. Legacy duration is read as a fallback without changing queue versions. Duration snapshots are materialized only during booking, clinical transitions and authorized schedule/duration mutations; schedule deactivation freezes existing durations before removing the template.
- Add `sessionId` (preferred) or `startTime` to appointment booking, reschedule, guest request, queue GET and call-next bodies/queries. Responses include `sessionId` and the snapshotted `startTime`. Legacy requests remain valid when a single session exists.
- Queue grouping, capacity, token allocation and duration snapshots use doctor/branch/date/startTime. Existing appointments preserve their snapshots and token numbers. Doctor-level transaction locks remain in place, so sessions cannot race schedule edits or transfers.
- Date exceptions accept `sessionId` to target one weekly session; legacy exceptions without it apply to all sessions for the date. Multiple exceptions require distinct session IDs.
- When a second weekly template is first added, exceptions authored under the former single-session model are transactionally bound to that original stable schedule ID, so their replacement timing is not copied onto the new session. Weekly edits are also checked against existing dated exceptions.
- `GET /api/appointments`, `GET /api/guest-requests` and `GET /api/reports` accept optional `sessionId` and `startTime`, applied in SQL before pagination/count and intersected with authorized scope. Use `startTime` with doctor/branch/date for snapshotted legacy appointments without a session ID. Guest receipt/staff items include nullable sessionId.

## Verification and development migration

- Development indexes were updated transactionally, without deleting or rewriting records: clinic/branch slug uniqueness; schedule start-time discriminator; exception session ID; appointment token/active-patient/current-consultation start-time discriminator. Production remains managed by Publish, with no startup/deploy DDL.
- Doctor-level advisory transaction locks remain unchanged and serialize schedule changes, booking, transfers and clinical transitions. Independent PostgreSQL contender tests include four concurrent bookings competing across two same-day sessions.
- A separate real PostgreSQL contention case gates both contenders on the clinic-slug lock and verifies the losing registration transaction leaves no admin, clinic, branch or QR behind.
- Migration `0008_consulting_admin_assignments.sql` updates existing ownership trigger functions, not trigger attachments. Clinic-only admin assignments still require the owning active admin; branch assignments additionally require that admin's active self-owned doctor profile and the matching active owned branch/clinic. The companion account guard permits that clinical capability without allowing role downgrade, deactivation while ownership exists, or a foreign doctor owner. Deferred ownership guards also recognize the self-owned clinical profile.
- The development migration was applied as one transaction with all triggers enabled. All ten live ownership trigger attachments were enumerated. The real PostgreSQL harness now installs the exact historical triggers from migrations 0002/0005/0006 followed by 0008, including last-owner protections and deferred guards. Live development service checks exercised both new-clinic `ownDoctor:true` and attaching a profile to an existing owning admin, forced deferred checks, and rolled back their temporary fixtures. The separate public screenshot fixture was not changed.
- Deployment must include this function migration through the managed Publish/schema deployment process; production was not altered, and there is no startup or deployment-command DDL. Do not declare production consulting-admin provisioning ready until the published database has the revised function definitions.
- Migration-chain audit found 0007 contains only staff session proofs. Migration `0009_public_slugs_session_isolation.sql` now persists all seven previously applied development indexes: clinic/branch slug uniqueness, weekly session and exception discriminators, appointment token, active-patient and current-consultation isolation. Its definitions match both the current Drizzle schema and inspected development indexes; the migration journal includes 0008 and 0009. No production DDL was run.
- The same audit found the pre-existing `guest_requests` table present in schema/development but missing from historical SQL files. `0010_guest_request_contract.sql` records that existing contract for fresh migration-based environments, without changing existing rows or introducing a second booking engine. All eleven SQL migration files now have matching journal entries.
- After final screenshots, the temporary public fixture was removed in one ownership-checked development transaction, including guest request, appointment/history, patient, QRs, schedules, duration/token settings, audit records, assignments, branches, doctor and both unlinked accounts. All ownership triggers stayed enabled. A scoped verification query across every affected table returned **0 remaining records**. `/tmp/clinic-expansion-public-fixture.json` is retained as a nonsecret evidence manifest with `cleanupPending:false` and `cleanupRemaining:0`; its old public URLs now intentionally no longer resolve.
