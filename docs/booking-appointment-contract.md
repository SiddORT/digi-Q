# Booking and appointment contract

## Scope and demonstrated discrepancies

ClinicFlow remains one product with its existing layout and styles. All creation entry points use **Visit details → Patient details → Confirmation → Ticket**. Only the explicit final confirmation creates the appointment and issued ticket. Reception approval is not part of this contract.

| Finding | Evidence and disposition |
| --- | --- |
| Initial `waiting` bookings were classified as queue events; own actor history was excluded | `workspace-features.ts` previously classified only `to_status` and excluded matching `actor_id`. Initial history (`from_status IS NULL`) now means **Booked / appointments**, including the owning admin's own action and public administrative audit actor. Stable history IDs/read state and scoped SQL remain; appointment audits stay excluded to avoid duplicate notices. Non-booking own actions remain excluded. |
| Owning-admin booking template implicitly disabled | `defaultTemplate` previously enabled only the primary recipient. Booking/clinicAdmin is now explicitly enabled by default. Other secondary roles/events retain their old opt-in behavior. Published overrides and clinic notification policies win; no settings rows were edited and no templates published. |
| Signed-in email outcome messages were duplicated/incomplete | Ticket already called `confirmationEmailMessage`; Booking added a second partial rendering. Removed the duplicate. Accepted, disabled, missing recipient, unavailable and uncertain outcomes share one truthful message. |
| Guest name and signed-in notes lacked useful hints; reschedule labels diverged | Shared `booking-fields.tsx` supplies terminology, optional/required metadata, placeholders and validation through existing `FormField`, care lookup, email, phone and date controls. Appointment details reuse the same labels. Optional-contact errors automatically open their section. |
| An explicit session could remain selected after eligibility changed | Previous daily-session resolution retained explicit rows irrespective of booking eligibility. Shared resolution rejects unavailable/capacity/mode/date/opening/break changes and missing IDs; alternatives are never silently substituted for an explicit selection. Valid sole options default; multiple eligible choices require selection. Operational historical-session filters intentionally are not booking eligibility filters. |
| Review could confirm different refreshed visit data | A review identity now includes clinic/location/doctor/date/mode and current session ID/range/timezone. Changed data disables final confirmation until reviewed again. Reschedule acknowledgement resets on session changes, and session-only edits count as dirty. |
| Patient policy hints used platform rather than selected clinic context | Public booking context now returns only the two relevant booking-policy scalars in addition to date boundaries. Account-linked mobile prerequisite and cancellation hints use the effective selected clinic policy. Guest contact remains optional; no clinical/private configuration is exposed. OpenAPI-generated clients/validators were regenerated. |

Already-correct behavior was extended, not replaced: staged flow, bounded scoped directory reads, cardinality-proven defaults, contextual registration, session allocator/transaction locks, stable retry identities, private tickets, confirmation claims and durable staff outbox. Separate patient confirmation and staff outbox are intentional, not evidence of double sending.

The reported missing slot remains unresolved without its exact authorized doctor/location/date/source/timezone context. An empty date does not establish that the doctor has no weekly sessions. Availability authoring, ownership/capacity changes, new permissions, broad column-width changes and deployment are outside this work.

## Mutation, notification and email mapping

1. Creation/reschedule retains existing allocation locks, duplicate-active-visit guards and stable request IDs/revisions. A failed submission writes no initial history/outbox; replay returns the same committed visit and does not allocate/send again.
2. Creation/reschedule seed the exact saved appointment observer and refresh visit-derived list/calendar/queue/context/dashboard/report/activity/notification/availability queries, without invalidating unrelated profile editors. Existing other appointment mutations retain their existing observer refreshes. Guest receipt recovery still uses its private secret; no contact is needed.
3. One initial history event generates one owning-admin in-app **Booked** notice after commit, including initial `waiting` status and self-created admin visits. History and audit are not shown twice. Read flags stay per user and scope remains server-authorized.
4. Valid patient email uses the existing durable primary claim, then the owning-admin booking job uses the existing durable asynchronous outbox claim. Both render committed reference, doctor, clinic/location, date, session range and timezone with parent display settings. Trimmed case-insensitive identical addresses are deduplicated across patient/admin and staff recipients.
5. Patient outcomes: accepted means provider acceptance only; disabled/missing recipient are known skips; unavailable does not undo the booking; uncertain status explicitly preserves the ticket and warns against another booking/automatic resend. Outbox timing/failure is independent of the saved visit and patient outcome. No simultaneity or SMTP inbox guarantee.
6. Unknown dispatch is terminal for automatic replay. Only known pre-dispatch failures can retry under the existing worker policy. Current eligibility and owner recipient are checked at dispatch; unrelated doctor/receptionist/event groups are unchanged.

### Configuration limits and owner activation

No live settings were queried or altered, no templates published, no real emails/appointments created and no deployment performed. Development transport remains intentionally disabled; controlled tests inject fictional transport before import.

Notifications must be enabled in effective platform/clinic policy, an active owning admin must have a valid address, and production SMTP must be configured for real delivery. Existing explicitly disabled **published** platform or clinic `booking/clinicAdmin` templates remain disabled; a template owner must intentionally review/activate them. A clinic notification opt-out remains authoritative. This work does not claim that any existing live clinic has been activated or that messages reached inboxes.
